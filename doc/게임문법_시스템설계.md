# 레크 게임 문법 시스템 (Game Grammar)
## — 유저가 규칙 코딩 없이 게임을 만들고, DB로 흘려보내는 구조

> 서비스의 진짜 해자: 게임을 우리가 다 만들지 않는다.
> 유저가 만든 게임이 검수를 거쳐 DB에 편입되고, 다시 추천 엔진에 들어가 재확산된다.
> **콘텐츠가 스스로 자라는 선순환.**

---

## 1. 핵심 통찰 — 모든 레크 게임은 부품의 조합이다

51개 게임을 해부하면, 결국 4개의 **원자 부품(atomic block)**으로 환원된다.
유저는 이 부품을 직접 다루지 않는다. **유형(archetype)을 고르면 부품이 자동 조립**된다.

### 4대 원자 부품
| 부품 | 역할 | 옵션 |
|---|---|---|
| **SCORE** | 점수 집계 | 없음 / 개인 / 팀(2~4팀), +/− 단위 |
| **TIMER** | 시간 제어 | 없음 / 카운트다운 / 랜덤폭발 |
| **POOL** | 콘텐츠(문제·단어·질문) | 없음 / 리스트 / Q&A쌍 |
| **FLOW** | 진행 방식 | 순서 / 지목 / 동시 / 릴레이 / 생존탈락 |

---

## 2. 게임 유형 (Archetype) — 유저가 고르는 단위

부품 조합으로 6개 유형이 나온다. **유저는 이 중 하나를 선택**하면 필요한 입력 폼이 자동 생성된다.

### ① 퀴즈형 (QUIZ)
- **부품**: POOL(Q&A) + SCORE + TIMER(선택)
- **유저 입력**: 문제·정답 리스트, 힌트(선택)
- **자동 제공**: 정답공개 버튼, 점수판, 타이머
- **예**: 초성퀴즈, 인물퀴즈, 스피드퀴즈
- **빌더 폼**: `[문제][정답][힌트]` 행 추가 반복

### ② 선택·토크형 (TALK)
- **부품**: POOL(질문) — 점수·타이머 없음
- **유저 입력**: 질문/선택지 리스트
- **자동 제공**: 다음 질문 넘기기, (밸런스면 A/B 표시)
- **예**: 밸런스게임, 만약에, 이심전심
- **빌더 폼**: `[질문]` 또는 `[선택A vs 선택B]` 행 추가

### ③ 서바이벌형 (SURVIVAL)
- **부품**: FLOW(생존탈락) + TIMER(선택)
- **유저 입력**: 룰 설명 + (지목 조건 리스트, 선택)
- **자동 제공**: 생존자 카운터, 탈락 처리, 순위 정렬
- **예**: 눈치게임, 손병호, 청개구리
- **빌더 폼**: `[룰 설명]` + `[조건]` 리스트(선택)

### ④ 퍼포먼스형 (PERFORM)
- **부품**: TIMER + SCORE + POOL(제시어, 선택)
- **유저 입력**: 제시어 리스트 + 제한시간
- **자동 제공**: 카운트다운, 통과/정답 카운터, 점수판
- **예**: 몸으로말해요, 랜덤플레이댄스
- **빌더 폼**: `[제시어]` 리스트 + `[시간]` 설정

### ⑤ 룰렛·추첨형 (PICK)
- **부품**: POOL + 랜덤추출
- **유저 입력**: 항목 리스트(벌칙·상품·이름)
- **자동 제공**: 룰렛 애니메이션, 랜덤 선정
- **예**: 벌칙룰렛, 복불복사다리
- **빌더 폼**: `[항목]` 리스트

### ⑥ 폭탄·긴장형 (BOMB)
- **부품**: TIMER(랜덤폭발) + FLOW(릴레이)
- **유저 입력**: 릴레이 규칙 + (미니 문제, 선택)
- **자동 제공**: 랜덤 폭발 타이머, 진동/사운드 연출
- **예**: 시한폭탄
- **빌더 폼**: `[규칙]` + `[미니문제]` 리스트(선택)

> **이 6개로 51개 게임의 95%가 커버된다.** 새 게임도 대부분 이 안에 떨어진다.
> 어디에도 안 맞는 진짜 새로운 규칙 → "기타/실험형"으로 받아 개발자 검수에서 판단.

## 3. 게임 메타데이터 (유형과 별개로 항상 입력)

어떤 유형이든 추천 엔진에 태우려면 아래 태그가 필요하다. 빌더 마지막 단계에서 입력.

```
{
  name: "게임 이름",
  archetype: "QUIZ | TALK | SURVIVAL | PERFORM | PICK | BOMB",
  phase: "opening | icebreak | main | finale",   // 큐시트 어디에 넣을지
  energy: 1~5,                                     // 텐션 (곡선 배치용)
  place: ["bus","room","hall"],                    // 가능한 장소
  mode: "solo | team | both",
  minPlayers, maxPlayers,
  duration: 분,
  materials: "없음 | 간식 등",                     // 준비물
  script: "진행 대본",
  pool: [...],                                     // 유형별 콘텐츠
}
```

> 유저가 태그를 잘못 달 수 있으므로, **일부는 자동 추론**:
> - archetype 고르면 → 기본 phase/energy 추천값 프리필
> - place는 체크박스, mode는 토글로 실수 최소화

## 4. 양방향 파이프라인 — 유저 창작 → DB 편입 → 재확산

```
[유저]                          [시스템]                    [개발자]
 새 게임 만들기
   유형 선택 ──────────────→ 부품 자동 조립
   콘텐츠 입력 ─────────────→ 진행 가능 여부 검증(자동)
   테스트 진행                 · 문제 0개? 룰 공백? 차단
   "추천하시겠습니까?" ─────→ [내 게임]으로 저장(로컬)
        │
        └─ "커뮤니티에 제안" ─→ 검수 대기열(pending) ──→ 검수 화면
                                                          · 승인 → 정식 DB 편입
                                                          · 반려(사유) → 유저에게
                                        ┌─────────────────────┘
                                        ↓
                              정식 게임으로 승격
                                        ↓
                    추천 엔진에 편입 → 다른 유저 큐시트에 등장
                    커뮤니티에 "○○님이 만든 게임" 노출
                                        ↓
                         응용/변형 제안 → 새 게임 파생 (선순환)
```

### 검수(개발자용) 화면이 봐야 할 것
- 게임 이름 + 유형 + 메타데이터
- 콘텐츠 풀 전체 (부적절·저작권·중복 체크)
- **자동 플래그**: 비속어 필터, 기존 게임과 유사도, 문제 수 부족
- 액션: **승인 / 반려(사유 입력) / 수정 요청**
- 승인 시: 원작자 크레딧 부여 → 커뮤니티 노출

### 커뮤니티 선순환의 동력
- **크레딧**: "이 게임 ○○님 제작" → 만들 동기
- **인기 지표**: 많이 쓰인 유저 게임 → "명예의 전당"
- **변형 제안**: 기존 게임에 "이렇게 바꿔보면?" → 파생 생성
- **시즌 챌린지**: "이번 달 새터 게임 공모" → 집단 창작

## 5. 유저 빌더 UX 흐름 (규칙 코딩 0)

```
STEP 1  어떤 유형의 게임인가요?
        [퀴즈] [토크] [서바이벌] [퍼포먼스] [룰렛] [폭탄]
        (각 카드에 "이런 게임: 초성퀴즈, 인물퀴즈" 예시)

STEP 2  게임 정보
        이름, 대본, 준비물

STEP 3  콘텐츠 채우기  (유형별 폼 자동 생성)
        예) 퀴즈형 → [문제][정답][힌트] 행 추가
            토크형 → [질문] 행 추가
            (CSV 붙여넣기 지원 → 대량 입력)

STEP 4  언제·어디서 쓰나요?  (메타데이터)
        phase(추천값 프리필) · 장소 · 인원 · 시간

STEP 5  테스트 진행 → "잘 돌아가나요?"
        실제 진행 화면 미리보기

STEP 6  "이 게임을 어떻게 할까요?"
        [나만 쓰기]  [커뮤니티에 추천하기 →검수]
```

> 핵심: **유저는 "규칙"을 만들지 않는다. "유형을 고르고 콘텐츠를 채운다".**
> 규칙(점수/타이머/진행)은 유형이 제공한다. 그래서 누구나 진행 가능한 게임이 나온다.

## 6. 데스크톱↔모바일 크로스 디바이스 설계

| 기기 | 역할 | 이유 |
|---|---|---|
| **데스크톱/웹** | 구성·창작·검수 | 큐시트 빌드, 게임 만들기, 문제 대량입력, 개발자 검수 → 넓은 화면·키보드 필요 |
| **모바일** | 현장 진행 | 대시보드·사운드보드·점수판 → 손에 들고 |
| **추출물** | 공유·백업 | PPT(대형화면용), 큐시트 PDF, 진행용 링크/QR |

### 연결 방식 (서버리스 유지)
- **PC에서 만든 큐시트 → 모바일로**: QR코드에 큐시트 데이터 인코딩(로컬) or 링크 공유
- **PPT 추출**: 큐시트의 퀴즈 문제·이미지를 슬라이드로 렌더 → 대강당 대형화면용
- **큐시트 PDF**: 진행 순서·대본·준비물 체크리스트 → 인쇄/공유

## 7. 이 시스템이 주는 전략적 가치

1. **콘텐츠 무한 확장**: 우리가 게임을 다 안 만들어도 유저가 채운다.
2. **네트워크 효과**: 유저 게임이 많아질수록 추천 품질↑ → 더 많은 유저.
3. **커뮤니티 락인**: 내가 만든 게임이 여기 있으니 떠나기 어렵다.
4. **검수로 품질 유지**: 아무거나 안 들어온다 → "터지는 게임만" 원칙 유지.
5. **데이터 자산**: 어떤 게임이 실제로 많이 쓰이는지 = 다음 기획의 근거.

- 개발자 검수 화면 (승인/반려)
- 반응형 (데스크톱 구성 → 모바일 진행)
