# 레크플러스 1차 제한 파일럿 — 상태·데이터 명령 계약

> 작성: 2026-09-11
> 범위: P01 초안. P03–P10의 migration/RPC 설계 기준
> 상태: 제품·운영 확정 전. `[결정 필요]` 값은 DB enum·기본값으로 만들지 않는다.

## 1. 고정 원칙

- 플랜은 편집 가능한 미래 계획이고, 실행은 시작 시점에 고정한 과거 원본이다.
- 모든 소유자 ID는 인증 컨텍스트에서 얻는다. 요청 본문의 `owner_id`는 받지 않거나 무시한다.
- `run_id`, `run_game_id`, `plan_item_id`, `request_id`는 UUID다. 재시도에서 새 UUID를 만들지 않는다.
- 시작·결과·종료·정정·후기·검수는 제한 RPC만 사용한다. 직접 테이블 DML은 이 불변 조건을 우회할 수 없어야 한다.
- 서버는 상태·revision·소유권·명령 순서·요청 본문 일치를 한 트랜잭션에서 검사하고, 같은 요청은 먼저 기존 영수증을 반환한다.

## 2. 핵심 데이터 단위

| 단위 | 식별자 | 불변/수정 규칙 | P03–P06 구조 |
|---|---|---|---|
| 게임 버전 | `game_version_id` | 본문·문항·준비물·제약·출처·크레딧을 함께 고정한다. 수정은 새 버전이다. | `game_versions`, `games.current_version_id` |
| 게임 제출본 | `submission_id`, revision | 작성 초안과 제출한 본문을 분리한다. 승인 전 원본을 직접 공개하지 않는다. | `game_submissions` |
| 행사 플랜 | `plan_id`, revision | 기대 revision이 같을 때만 원자 저장한다. | `event_plans` 확장 |
| 플랜 항목 | `plan_item_id` | 재정렬해도 유지하고 삭제 뒤 재사용하지 않는다. | `event_plan_games` 확장 |
| 행사 실행 | `run_id` | 시작 때 새로 만들며, 종료 뒤 일반 덮어쓰기를 금지한다. | `event_runs` |
| 실행 게임 | `run_game_id` | 플랜 항목·버전·정렬·배정 시간·본문·문항·조건 스냅샷을 보존한다. | `event_run_games` |
| 실행 이벤트 | `request_id`, `event_sequence` | 원본 명령과 서버 영수증이다. `event_sequence`는 실행별 단조 증가한다. | `run_events`/영수증 구조 |
| 후기 | `review_id`, revision | 유일키는 `(run_id, game_version_id)`다. 본문 수정은 revision을 올린다. | `game_reviews`/revision 보관 |

### 2.1 행사 조건 계약

| 필드 | 저장 규칙 | 공개 규칙 |
|---|---|---|
| `event_group` | `school`, `university`, `company`, `private_or_other` 중 하나. 필수 | 범주만 가능 |
| `people_count` | 양의 정수. 입력 중 빈 문자열은 UI에서 허용하되 저장/시작 전 거부 | 정확한 값 금지 |
| `people_band` | `people_count`에서 서버가 산출 | D01의 구간 확정 전 공개 금지 |
| `target_minutes` | 1–1440 정수. 필수 | 공개 DTO에는 포함하지 않음 |
| `place` | `room`, `restaurant`, `hall`, `bus`, `outdoor`, `other` 중 하나. 필수 | 범주만 가능 |
| `constraints` | 명시적으로 선택한 제약의 문자열 집합 | 공개 허용한 값만 포함 |
| `event_type` | 선택 텍스트/선택값. MT·OT 등은 추천 필수값이 아님 | 기본 비공개 |

게임 제약 메타데이터는 각 제약마다 `present`, `absent`, `unknown`을 구분한다. 사용자가 제외를 요구한 위험이 `unknown`이면 자동 추천에서 제외하고 이유를 표시한다. 이 배제 정책은 D02 담당 확인 전 UI 문구와 DB 제약으로 고정하지 않는다.

### 2.2 준비물 계약

게임 버전의 준비물은 `{ name, quantity_text, alternatives }[]`다. `quantity_text`는 자유 텍스트이며 기존 `preparations` 문자열에서 수량을 추정하지 않는다. 자동 합산, 구매 링크, 가격 정보는 1차 범위 밖이다.

## 3. 상태 전환

### 3.1 플랜과 실행

| 대상 | 전환/명령 | 수행자·사전조건 | 거부/공개 영향 |
|---|---|---|---|
| 플랜 | 저장/재정렬 | 소유자, `expected_revision` 일치 | 불일치면 `revision_conflict`; 과거 실행 스냅샷은 불변 |
| 실행 | `start_run` → `active` | 소유 플랜, 최소 1개 항목, 버전 접근 가능, 주 기기 등록 | 빈 실행·타인 플랜·버전 누락 거부; 새 `run_id`만 생성 |
| 실행 | `finish_run` → `finished` | active, playing 항목 0개, 마지막 명령까지 서버 수락 | pending은 보존; 자동 completed 금지 |
| 실행 | `abort_run` → `aborted` | active, playing 항목 0개, 중단 사유 | pending은 보존; 완료 지표 포함 여부는 D03 |
| 실행 | 종료 후 정정 | 소유자 또는 별도 권한, 사유, 기대 revision | 기존 이벤트를 바꾸지 않고 새 정정 이벤트; 후기 자격 재검증 |

### 3.2 실행 게임

| 현재 | 허용 전환 | 필수 입력 | 일반 저장에서 거부 |
|---|---|---|---|
| `pending` | `playing` | request ID, 다음 event sequence | 종료 실행, 다른 기기, 역순 명령 |
| `pending` | `skipped` | request ID, 사유 | `completed`로의 암묵 변환 |
| `playing` | `completed` | request ID, 결과와 선택 측정 시간 | 종료 실행, event sequence 누락 |
| `playing` | `skipped` | request ID, 사유 | 상태 역전환 |
| `completed`/`skipped` | 없음 | 정정 RPC의 사유와 새 이벤트만 허용 | 일반 update, 과거 이벤트 수정 |

### 3.3 후기와 공개 상태

| 상태 | 허용 명령 | 서버 검증 | 공개 영향 |
|---|---|---|---|
| `private` | 저장/수정, 공개 제출 | 본인 소유·서버 동기화·해당 버전 completed, 필수 결과/재사용 의향 | 비공개 |
| `pending` | 수정/철회, 검수 | 수정은 새 revision 및 `private` 복귀; 제출은 동의 증거 고정 | 비공개 |
| `published` | 수정/철회, 관리자 숨김 | 수정 즉시 `private`; 철회는 작성자 명령 | 즉시 공개 DTO 제외 |
| `changes_requested`/`rejected` | 수정 후 재제출 | 최신 revision·동의 재확인 | 비공개 |
| 관리자 숨김 | 복구 | 현재 동의·자격·최신 revision·숨김 해소 사유 | 자동 재공개 금지 |

후기 자격은 완료 지표와 다르다. `completed`인 본인 소유 실행 게임이 하나 이상 있고 실행 종료 명령이 서버 반영되면 해당 게임 버전 후기 하나를 저장할 수 있다. skipped만 있는 실행, 타인 실행, 미동기화 실행, 다른 버전은 거부한다.

## 4. 완료 지표

```text
N = 시작 스냅샷 게임 수 (N = 0이면 시작 거부)
C = 서버 원본에서 계산한 completed 수
threshold = N == 1 ? 1 : max(2, ceil(N * 0.5))
qualifies_for_completion_metric =
  C >= threshold AND 명시적 종료 AND 마지막 명령까지 서버 반영 AND NOT practice
```

경계: `N=1→1`, `N=2→2`, `N=3→2`, `N=4→2`, `N=5→3`. `finished`와 `aborted`는 완료 지표와 다른 상태다. aborted를 완료율 분자에 포함할지와 미종료 관찰 기간은 D03 결정 전 계산하지 않는다.

## 5. 명령·재전송·오류 응답

모든 변경 명령은 `request_id`, `expected_revision`(생성 명령 제외)을 받는다. 클라이언트 기록 시각은 D08 보유 정책이 확정되기 전 서버에 보내거나 저장하지 않는다. 서버는 `revision`, `server_received_at`, 동일 요청의 재사용 여부를 반환하고, `local_pending` 등 동기화 상태는 계정별 outbox가 별도로 관리한다. 같은 `request_id`에 다른 사용자 또는 다른 본문 해시는 `request_id_reused`로 거부한다.

| 오류 코드 | 사용자 조치 |
|---|---|
| `authentication_required` | 로그인 후 다시 시도 |
| `forbidden` | 소유자/역할 확인 필요 |
| `state_mismatch` | 최신 상태를 확인하고 결과 선택 |
| `revision_conflict` | 동기화를 멈추고 사용자 선택으로 해결 |
| `request_id_reused` | 새 명령으로 다시 작성 |
| `missing_prior_event` | 같은 실행의 앞선 대기 명령부터 전송 |
| `primary_device_mismatch` | 원래 주 기기에서 재개 또는 지원 절차 |
| `sync_incomplete` | 동기화 완료 뒤 후기 작성 |
| `review_not_eligible` | 완료/소유/버전 조건을 확인 |

네트워크 오류는 재시도 가능이고, 위 오류는 사용자 조치가 필요한 실패다. outbox는 실행별 순서대로 보내며 서버 영수증을 영속한 뒤에만 항목을 지운다.

## 6. 공개 DTO 경계

공개 응답에는 공개 후기 ID, 게임/버전 식별자, 구조화 결과·팁, 공개 동의한 크레딧, 행사군·인원 구간·장소·공개 허용 조건, 검수된 주의사항, 공개 중인 연결 후기 수만 포함한다.

원본 run/plan/owner ID, 이메일, 정확한 인원, 기술 시각, 비공개 정답, 진행자 전용 문항, 신고자, 내부 검수 메모는 DTO·HTML·RSC·metadata에 포함하지 않는다. 진행용 비공개 문항은 실행 권한을 검사하는 전용 경로로만 준비한다. 공개 후기와 검수 상태는 영속 오프라인 캐시에서 제외한다.

## 8. 계약 테스트 입력표

| 입력 | 기대 결과 | 책임 티켓 |
|---|---|---|
| 같은 플랜에서 두 번 시작 | 서로 다른 run 2개, 첫 스냅샷 유지 | P04–P08 |
| `N=5`, completed 1개, 종료 | 지표 미달, completed 게임 후기 가능 | P08, P09 |
| 마지막 게임이 playing인 종료 | 자동 완료 없이 결과 선택 요구 | P08, P18 |
| 동일 결과 명령을 3회 재전송 | 결과·이벤트·revision 각 하나, 영수증 재사용 | P08, P14 |
| 동일 request ID의 다른 본문 | `request_id_reused` | P07–P10 |
| completed를 skipped로 정정 | 원 이벤트 보존, 새 이력, 연결 공개 후기 즉시 비공개 | P08–P10 |
| 비회원 공개 상세 조회 | answer/run ID/정확한 인원/내부 메모 없음 | P12, P21 |
| U1 로그아웃 뒤 U2 로그인 | U1 outbox·응답·캐시가 U2에 미반영 | P13–P16 |
