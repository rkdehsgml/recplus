# 레크플러스 1차 제한 파일럿 — 개발 실행계획

> 작성: 2026-09-11 / 마지막 현황 갱신: 2026-09-16 / 상태: 로컬 기반 구현 진행 중, 파일럿 개방 전  
> 상위 기준: [확정 제품 결정문](./제품결정_행사진행기록_후기파일럿.md)  
> 구현 대상: `web/`, Supabase 데이터 계약. 이 문서는 확정 범위를 개발 단위로 나누며 제품 결정문을 대체하지 않는다.  
> 조사 범위: 현재 체크아웃의 코드·마이그레이션·검증 스크립트. 실제 운영/스테이징 DB 적용 상태, 계정, 백업 복구는 이번 작업에서 검증하지 않았다.

## 1. 이번 계획에서 개발 가능한 단위로 바꾼 것

1. **00 적용 감사 → 01 정책·상태 계약 → 02 마이그레이션 → 03 RPC·RLS → 04 로컬·오프라인 → 05 사용자 화면 → 06 공개·검수 → 07 E2E·운영** 순서를 유지한다.
2. 단계 안의 작업을 PR 단위로 분리한다. 각 티켓은 아래의 산출물과 완료 기준을 함께 충족해야 끝난다. UI 목업이나 SQL 파일 작성만으로 완료 처리하지 않는다.
3. 구현은 기능 플래그 뒤에서 진행한다. 파일럿 계정에 실제로 여는 시점은 07 통과 후다. 코드 병합·스테이징 적용·파일럿 개방을 구분한다.
4. 지금 바로 할 일은 **P00의 실제 환경 감사 준비 및 수행, P01의 계약 구체화**다. P00의 로컬 코드 조사는 이 문서로 수행했지만 P00 전체가 완료된 것은 아니다.
5. 제품 결정문 6.1의 시작 조건은 제품 구현 착수 게이트다. 조건이 갖춰지기 전에도 감사 자료·정책 초안·테스트 시나리오는 준비할 수 있으나, 미정 정책을 임의로 DB에 굳히지 않는다.

## 3. DB 적용 전에 닫아야 할 구체값

제품의 큰 방향은 확정되어 있다. 다음 세부값은 원문에 없거나 구현상 해석이 필요하다. **아래 권장안은 확정 정책으로 간주하지 않는다.** P01/P02 계약 문서에 담당자·결정일·최종값을 기록하고 이 표의 상태를 갱신한다.

| ID | 확정할 값 | 구현용 권장안 또는 필요한 결정 | 담당 / 차단 지점 |
|---|---|---|---|
| D01 | 공개 인원 구간·입력 범위·기존 조건 누락 | 구간 초안: 1–9 / 10–19 / 20–39 / 40–79 / 80명 이상. 입력 중 빈 문자열을 허용하고 확정 시 양의 정수 검증. 구형 데이터의 행사군을 대학으로 추정하지 말고 다음 시작 전 보완 | 제품 / P04 |
| D02 | 명시 제약과 `미확인`의 추천 처리 | 게임 메타데이터는 `있음/없음/미확인`. 사용자가 제외를 요구한 위험이 미확인이면 자동 추천에서 제외하고 이유 표시하는 안. 행사군 적합성도 근거 없는 값을 추정하지 않음 | 제품·콘텐츠 / P03, P17 |
| D03 | `finished`와 `aborted`, 미종료 관찰 기간 | `finished`는 운영자가 종료를 확정한 실행, `aborted`는 중단 종료를 확정한 실행으로 구분하는 안. 둘 다 완료 게임 후기는 가능. 완료 지표에 aborted를 포함할지는 원문 수식과 대조해 명시. 미종료를 분모에 넣는 관찰 기간은 숫자로 확정 필요 | 제품·운영 / P05, P08, P26 |
| D04 | 보유·삭제·탈퇴·공개 동의 | 행사 원본/로컬 대기 데이터/후기/신고/감사/백업 각각 보유기간, 삭제 기산점·유예·복원 시 삭제 재적용, 탈퇴 시 연결 처리. 공개 동의 문안·버전과 콘텐츠 이용허락 확정 | 제품·운영 / P02, 모든 데이터 마이그레이션 적용 |
| D05 | 후기 1개 UX와 유일키 | 1차에서는 종료 화면에서 한 게임의 후기만 요청하고 추가 후기 유도는 하지 않음. DB 유일키는 확정문대로 실행+게임 버전 유지. 실행 전체에 unique를 추가하지 않음 | 제품 / P09, P19 |
| D06 | 게임 정정으로 후기 자격이 사라지는 경우 | completed→skipped 정정 시 연결 후기를 즉시 비공개로 전환하고 사유·이력 보존하는 안. 자격을 다시 얻어도 자동 재공개하지 않음 | 제품·검수 / P09, P10 |
| D07 | 주 기기와 오프라인 시작 | 사전 로그인·계정 귀속·버전 패키지 준비를 마친 주 기기에서 오프라인 새 실행 허용하는 안. 서버 동기화 전 후기는 잠금. 다른 기기 진행은 차단하며 자동 기기 인수는 제공하지 않음 | 제품·개발 / P08, P14 |
| D08 | 정확한 행사 일시와 기술 시각 | 행사 예정 일시 입력은 만들지 않음. 요청 client/server 시각은 무결성·복구용 비공개 기술 데이터. 실제 행사 일시처럼 공개/인증하지 않음. 재사용 날짜·작성 시간 계측의 최소 정밀도와 보유기간 확정 | 제품·운영 / P02, P26 |
| D09 | 검수·신고 운영과 신원 열람 | 운영자/검수자/이의제기 연락 경로, 심각도·처리 목표시간, 신고자 또는 행사 열람이 필요한 지원 사유와 별도 권한. 공개 크레딧의 별칭·동의 정책 | 운영 / P02, P10, P23, 개방 |

스테이징·4계정·운영 연락 담당자가 확보됐는지도 P00/P02에서 확인한다. 미확보를 구현 오류처럼 처리하거나, 확인하지 않고 확보됨으로 표시하지 않는다.

## 4. 공통 구현 계약

다음은 티켓을 나누더라도 공유해야 하는 기술 설계 기준이다. 구체 함수명·필드명은 P01에서 고정한다.

### 4.1 식별자와 원본

- `plan_id`: 편집 가능한 큐시트. `revision`을 기준으로 저장 충돌을 감지한다.
- `plan_item_id`: 순서와 별개인 UUID. 정렬 시 유지하고 항목 추가 시 새로 만든다.
- `run_id`: 사용자가 새 행사 시작을 선택할 때 기기에서 UUID 생성·영속 저장. 같은 시작 재전송은 같은 ID, 재진행은 새 ID다.
- `run_game_id`: 실행 안 항목의 고유 ID. `plan_item_id`, `game_id`, `game_version_id`, 시작 순서·배정 시간·본문·문항·조건을 보존한다.
- `game_version_id`: 본문과 문항까지 고정한 버전. 개인 문항 팩/수정 게임을 사용했다면 실제 실행 내용이 다른 공개 버전의 후기처럼 연결되면 안 된다. 소유자 전용 버전 또는 실행 변형을 식별하고 공개 자격을 P01에서 정의한다. 미해결 버전은 최신 버전으로 임의 연결하지 않는다.
- `request_id`: 논리적 명령마다 한 번 만들고 로컬 상태·outbox와 함께 저장한다. 재시도에서 다시 만들지 않는다.
- 실행 스냅샷은 서버가 접근 가능한 버전·소유 플랜으로 검증한다. 임의 JSON을 공인 버전 스냅샷으로 신뢰하지 않는다. 오프라인에서는 준비한 버전 식별자/해시를 함께 보관한다.

### 4.2 상태와 재전송

| 대상 | 계약 |
|---|---|
| 실행 게임 | `pending → playing → completed / skipped`, 시작하지 않고 스킵하는 `pending → skipped`도 사유와 함께 기록. 임의 역전환은 일반 저장에서 거부하고 정정 경로로 분리 |
| 실행 | 활성 실행 → `finished / aborted`. playing 항목이 남으면 먼저 결과를 선택하도록 안내하고 자동 완료하지 않음. pending 잔여 항목은 종료 스냅샷에 그대로 보존하는 안을 P01에서 확정 |
| 복구 상태 | 타이머·점수·문항 위치 등 자주 바뀌는 상태. 실행 주요 이벤트와 분리하고 계정+run 기준 저장. 참가자 자유입력 이름은 전송하지 않음 |
| 동기화 | `local_pending / syncing / synced / conflict / failed`. 단순 요청 성공이 아니라 해당 실행의 마지막 명령까지 서버가 수락했는지 확인 |
| 후기 | `private → pending → published / changes_requested / rejected`. 수정은 새 revision. published 수정은 즉시 private, 재제출은 새 본문에 대한 동의 증거 보존 |
| 철회·긴급 숨김 | 작성자 철회와 관리자 숨김을 별도 사유/상태로 구별. 복구는 현재 동의·자격·revision·숨김 사유 해소를 재확인. 철회나 최신 수정본을 과거 승인으로 되살리지 않음 |

변경 RPC는 인증 사용자, 대상 소유/역할, 현재 상태, `expected_revision`, 멱등 요청을 한 트랜잭션에서 확인한다. 서버가 결과·revision·접수 시각을 반환한다. 시작·종료·후기·검수의 직접 테이블 쓰기는 허용하지 않는다.

**중복 요청은 충돌 검사보다 먼저 이미 처리한 결과를 반환**하되 사용자와 요청 본문 일치를 확인한다. 같은 request ID에 다른 본문은 오류다. revision이 바뀐 정상 재전송을 충돌로 오인하면 안 된다. 초기 생성처럼 revision이 없는 명령은 ID 유일 제약으로 보호한다.

게임 이벤트에는 실행 내 단조 증가 순서를 부여한다. 역순 요청은 적용하지 않고 대기/충돌로 반환한다. outbox는 실행별 순차 전송하고 영수증 저장 전 항목을 지우지 않는다. 시간 비교만으로 최종 쓰기를 선택하지 않는다. 수정·정정은 새 명령이며 과거 명령을 변조하지 않는다.

권장 오류 계약: 인증 필요, 권한 없음, 상태 불일치, revision 충돌, 요청 ID 재사용, 선행 명령 누락, 동기화 미완료, 후기 자격 없음, 주 기기 불일치. 재시도 가능한 네트워크 오류와 사용자 조치가 필요한 오류를 구분한다.

### 4.3 완료 지표와 후기 자격

```text
N = 시작 스냅샷 게임 수 (빈 실행은 시작 불가)
C = 서버 원본에서 계산한 completed 수
threshold = N == 1 ? 1 : max(2, ceil(N * 0.5))
qualifies_for_completion_metric =
  C >= threshold AND 명시적 종료 AND 모든 종료 명령 서버 반영 AND NOT 연습/테스트
```

`finished/aborted` 적용은 D03으로 고정한다. 완료 여부를 클라이언트가 쓰지 못하게 한다. 분모 N은 정렬·플랜 편집·정정으로 줄이지 않는다. 최소 경계 사례는 N=1→1, 2→2, 3→2, 4→2, 5→3이다.

후기 자격은 **본인 소유 + 종료되어 서버에 동기화된 실행 + 해당 버전의 completed 항목 존재**다. 완료 지표 통과는 요구하지 않는다. 동일 버전이 실행에 여러 번 있으면 그중 실제 완료한 `run_game_id`를 근거로 저장하되, 후기 유일성은 실행+버전이다. 후기 저장·제출·공개 직전에 자격을 각각 검증한다.

### 4.4 공개 및 오프라인 경계

- 공개 DTO는 허용 필드만 명시한다: 공개 후기 ID, 게임/버전 식별자, 구조화 결과·팁, 공개 동의한 크레딧, 행사군·인원 구간·장소·공개 허용 조건, 검수된 주의사항, 공개 중인 연결 후기 수.
- 원본 run/plan/owner ID, 이메일, 정확한 인원·기술 시각, 비공개 정답·host-only 문항, 신고자, 내부 검수 메모를 DTO·HTML·RSC·메타데이터에 싣지 않는다. 작성자에게 보여줄 수정 요청 사유와 내부 메모는 별도 필드다.
- 진행 필수 비공개 문항은 소유 실행/사용 권한 검사를 거친 전용 조회로 준비한다. 공개 정답 숨김 CSS를 보안 경계로 사용하지 않는다.
- 공개 후기와 검수 상태는 파일럿 동안 영속 오프라인 캐시 대상에서 제외하는 안을 적용한다. 온라인 공개 응답은 no-store 또는 검수와 연동한 무효화로 철회·숨김을 반영한다. 로컬 시드도 숨김 게임을 복원하지 못해야 한다.
- **이미 전송된 화면이나 네트워크가 끊긴 기기의 자료를 원격으로 즉시 회수할 수는 없다.** 서버/온라인 API·후속 탐색·새로고침·활성 화면 재조회에서 즉시 제외됨을 출시 기준으로 정의하고, 진행용 비공개 스냅샷은 공개 목록과 분리한다. 열린 온라인 화면의 재검증 방식·허용 지연은 P01/P21에서 명시한다.

### 02 — 마이그레이션

이 단계의 migration은 **기본 접근 차단, RLS 활성화, 함수 실행 권한 제한**까지 포함한다. 다음 단계에서 허용 경로를 연다. 빈 권한 테스트는 충분하지 않으며 이관 무결성 테스트가 같이 필요하다. 과거 migration을 수정하지 않고 신규 파일로 추가한다.

**P03. 게임 버전·제출본·출처 이관** · 선행 P01, P02

- 위치: `web/supabase/migrations/` 및 이관 검증 SQL(신규). `game_versions`, `game_submissions`, `games.current_version_id`, `parent_game_id`, 크레딧/편집 revision을 추가한다.
- 기존 게임 ID·작성 내용·소유·출처·동의 증거를 보존한다. 제출 전 개인 초안은 비공개로 유지하고 제출본은 별도로 고정한다. 기존 공개 행의 동의 근거가 부족하면 목록화해 개별 처리하며 신규 동의를 만들어 넣지 않는다.
- 완료: 이전 본문·문항 해시 대조, 버전 수정/삭제 거부, 잘못된 current version FK 거부, 재실행 가능한 이관. 구형 저장 함수가 새 버전 원본을 우회 갱신하지 못하도록 적용 순서를 명시한다.

**P04. 플랜 revision·항목 ID·행사 조건 이관** · 선행 P03

- 위치: migrations, 계획 타입 계약. 플랜 조건 축·revision, 항목 UUID와 버전 참조를 추가하고 `(plan_id, position)`은 순서 유일성으로 유지한다.
- 기존 항목에 ID를 한 번 부여한다. 행사군/제약 등 모르는 정보는 이관 미완료로 구분하고 다음 새 실행 전에 보완한다. 기존 플랜 삭제가 과거 실행을 cascade 삭제하지 않게 참조 정책을 정한다.
- 완료: 순서 변경 후 항목 ID 유지, 레거시 플랜 수/내용 일치, 잘못된 조건 거부, 같은 순서 중복 거부.

**P05. 실행 원본·이벤트·복구 참조 구조** · 선행 P04

- 위치: migrations. `event_runs`, `event_run_games`, `run_events`, 멱등 처리 결과 보관 구조. 시작 스냅샷·상태·기술 시각·실행 순서·주 기기·revision·연습 플래그를 저장한다.
- 게임 결과·시작·종료·정정 이벤트만 감사 가능한 원본으로 보관한다. 타이머 tick은 주요 이벤트로 만들지 않는다. `play_sessions`의 기존 최종 상태를 과거 실제 실행 이력으로 날조하지 않는다.
- 완료: 동일 큐시트의 독립 실행 2개 보관, 완료/중단 기록 보존, FK 교차 소유 위조 차단에 필요한 관계 제약, 이벤트 request ID 중복 방지, 종료 후 원본 덮어쓰기 방지.

**P06. 후기·신고·감사·보유 정책 구조** · 선행 P05

- 위치: migrations. `game_reviews`, 제출/편집 revision 보관, `content_reports`, `moderation_actions`, 공개 동의 증거. 필요한 보조 테이블은 계약에 명시한다.
- 후기 `(run_id, game_version_id)` 유일. 결과·재사용 의향 필수, 실제 소요시간 null/모름, 콘솔 측정 시간 별도, 고정 문제 태그, 팁 200자. 신고/감사는 nullable FK들+정확히 하나의 대상 CHECK 또는 대상별 테이블로 실제 FK를 보장하며 문자열 target ID만 두지 않는다.
- 완료: 교차 게임/버전/실행 참조 실패, 원문·동의 revision 보존, 비공개 기본값, 탈퇴·콘텐츠 삭제 시 승인된 보유 정책대로 처리. 감사 FK 때문에 계정 삭제가 실패하거나 삭제 cascade로 필요한 증거가 유실되지 않는다.

### 03 — 제한 RPC·RLS 및 서버 응답

**P07. revision 기반 큐시트 저장** · 선행 P06

- 위치: 신규 `save_event_plan` 계약과 소유 읽기 정책, 추후 `event-plan-store.ts`에서 쓸 어댑터 계약.
- `expected_revision` 일치 시 플랜·항목을 원자 반영하고 안정적 항목 ID 유지. 클라이언트 owner 지정은 무시/거부한다. 직접 부모·자식 쓰기로 RPC 조건을 우회할 수 없게 한다.
- 완료: 오래된 저장과 타인 항목 삽입 실패, 중복 저장 3회에도 결과 하나, 최신 플랜을 덮어쓰지 않는 충돌 응답. 실행 생성 후 플랜 편집이 실행 스냅샷을 바꾸지 않음.

**P08. 실행 시작·게임 결과·종료·정정 명령** · 선행 P07

- 위치: 시작/결과/종료/정정 RPC(신규), `web/src/lib/event-run-store.ts`(신규 예정 계약). 인증·주 기기·명령 순서·revision 검증 후 이벤트와 현재 투영 상태를 한 트랜잭션으로 갱신한다.
- 시작 시 플랜/버전을 검증해 스냅샷을 고정한다. 게임 완료/스킵에 사유·측정 시간을 저장한다. 종료는 게임 상태를 자동 변경하지 않고 서버가 완료 판정을 계산한다. 종료 후 정정은 사유 필수의 추가 이력이며 원 스냅샷 불변.
- 완료: 동작별 3회 재전송 결과 하나, 응답 유실 후 재시도 성공, 역순 적용 거부, 타인/다른 기기/종료 후 일반 쓰기 거부, 완료 수식 경계 통과. 기기 점수/이름 JSON을 무검증 업로드하지 않음.

**P09. 후기 저장·제출·수정·철회** · 선행 P08

**P10. 통합 검수·숨김·복구·감사 명령** · 선행 P09

### 04 — 계정별 로컬·오프라인 기반

**P13. 계정별 저장 및 레거시 격리** · 선행 P12

- 위치: `cuesheets.ts`, `play-session.ts`, `custom-games.ts`, `item-packs.ts`, 각 cloud store, 로그인/로그아웃·큐시트 로딩 경로.

- 로그아웃/계정 전환 시 읽기 캐시·메모리·진행 중 요청을 무효화하고 sync worker를 멈춘다. U1 요청의 늦은 응답도 U2 저장 공간에 반영하지 않는다. 대기 데이터는 U1 전용으로 보관하여 재로그인 때만 재개한다.
- 완료: U1→로그아웃→U2 전환, 같은 브라우저 다른 탭, 재시작, 늦은 fetch 응답에 U1 데이터 노출/업로드 0건. 소유 불명 레거시 자동 귀속 없음.

**P14. 원자 로컬 저장·outbox·멱등 동기화** · 선행 P13

- 위치: `web/src/lib/offline/`(신규). IndexedDB 트랜잭션으로 명령·로컬 투영 상태·요청 ID를 함께 저장하고 실행별 순서로 전송한다. 기존 timestamp 우선 병합을 명령 영수증 기반으로 교체한다.
- 서버 응답 유실/앱 종료 시 같은 요청을 재전송한다. revision 충돌은 대기열을 멈추고 사용자 선택으로 해결하며 조용히 최신 값으로 덮어쓰지 않는다. 토큰 만료는 재인증 대기, 다른 사용자 로그인은 전송 금지다.
- 완료: 오프라인 시작→완료→스킵→종료→브라우저 재시작→재연결 후 순서·수량 일치. 로컬 저장 용량 초과/트랜잭션 실패 시 `기기에 저장됨`을 표시하지 않는다. 서버 반영 전엔 후기 제출 불가.

**P15. 시작 전 오프라인 패키지·서비스 워커** · 선행 P14

**P16. 복구 상태·주 기기 충돌 처리** · 선행 P15

- 신고 접수/처리 상태·사유를 보존하고 권한 있는 신고자에게 필요한 처리 결과만 제공한다. 신고자의 신원과 원본 비공개 실행을 일반 검수 목록에 포함하지 않는다.
- 필요한 지원 열람은 별도 권한·사유·감사 기록을 거치게 한다. 신고 이의제기 연락 경로를 노출한다.
- 완료: 신고 다수로 자동 숨김 없음, 중복 클릭 멱등 처리, 신고자 노출 없음, 숨김/복구/철회 경합의 화면·감사 일치.

### 07 — E2E·개방·파일럿 관찰

**P24. DB·권한·무결성 자동 회귀** · 선행 P23

- 위치: `web/supabase/tests/`(신규), `web/scripts/`의 파일럿 검증기(신규), package scripts. 각 P03–P12에서 만든 검사를 통합한다.
- 기존 `e2e:supabase`와 별도 명령으로 U1/U2/A1/A2/비회원 JWT를 사용한다. 스테이징 대상 확인을 강제하고 실행별 격리 데이터와 정리 절차를 둔다. service role 조회만으로 통과하지 않는다.
- 완료: 아래 테스트 표 전체와 원본↔화면용 응답 대조 통과. 사용자·관리자 권한을 같은 계정으로 바꿔 테스트한 결과를 4계정 테스트로 세지 않음.

**P25. 모바일·4계정·2기기 실제 브라우저 E2E** · 선행 P24

- 산출물: `doc/파일럿_E2E결과.md`(신규). 세션·기기·브라우저·빌드·DB revision·기대/실제·증거를 기록한다.
- 주 모바일 기기에서 시작→네트워크 중단→완료/스킵→종료→브라우저 재시작→재연결→후기→제출, 기기2에서 충돌·관리자 검수·철회를 확인한다. 작은 모바일 폭과 실제 브라우저 재시작을 포함한다.
- 완료: 정적 검사/DB 테스트/브라우저 E2E 각각 별도 결과. 콘솔 타이머·점수·문항 순서·준비물 복구 확인. 접속 불가나 계정 미확보는 미검증으로 표시한다.

**P26. 운영 런북·최소 계측·제한 개방** · 선행 P25 및 P00/P02 외부 조건 재확인

- 산출물: `doc/파일럿_운영런북.md`(신규), 내부 집계 쿼리·작성 시간 계측. 담당자, 계정 배포, 검수/신고 처리, 충돌/동기화 실패/주 기기 분실, 긴급 비공개, 백업 복구, 탈퇴 절차를 실행 가능한 순서로 쓴다.
- 공개 단계는 서버 기능 플래그/참여자 권한으로 제한한다. 정적 클라이언트 플래그만으로 API를 열지 않는다. 중대 권한 누락·기록 손실·미검수 공개가 나오면 개방 중지 후 원본을 보존하고 복구한다.
- 파일럿 내부 지표: 5팀 이상·실제 동기화 행사 20건 이상, 2팀 이상 다른 날짜 재사용, 완료 행사 중 후기 1개 이상 비율 40% 이상, 후기 작성 중앙 시간 90초 이하(목표 60초). 후기 작성 시간의 시작/저장/중단 처리와 관찰 종료일을 정의하고 필요한 최소 데이터만 수집한다.
- 완료: 기술 출시 통과표와 실사용 결과표를 분리하고, 원본·UI 표본 일치 100%/복구 불가 손실 0건을 확인. 학교·회사 행사는 첫 모집 지표에서 제외. 수요가 확인되기 전 2단계 기능을 자동 착수하지 않는다.

## 7. 적용·전환·복구 순서

1. **감사/리허설:** 실제 적용 상태와 백업 복원을 확인하고 D01–D09를 닫는다. 기존 공개/비공개·소유·동의별 기준 수량을 보관한다.
2. **추가 구조:** 새 테이블/컬럼/버전을 접근 차단 상태로 추가하고 기존 데이터를 이관·대조한다. 필수 불변 조건과 접근 통제를 migration에서 함께 적용한다.
3. **신규 쓰기 전환:** 제한 RPC·기능 플래그를 준비하고 새 클라이언트는 실행 원본에만 쓴다. 기존 복구 세션을 실행 원본으로 이중 쓰지 않는다. 이관 중 카탈로그/플랜 변경은 쓰기 제한 또는 검증된 호환 어댑터로 통제하고 최종 차이를 재대조한다.
4. **구경로 차단:** 오래 열린 탭·구 클라이언트의 직접 쓰기/구 RPC는 명확한 갱신 필요 오류로 거부한다. 개인 데이터 자동 업로드·종료 자동 완료·원본 공개 읽기 우회를 닫고 회귀 검증한다.
5. **스테이징 완주:** P24/P25 통과와 백업 이후 신규 데이터 복구 절차까지 확인한다. 플래그가 꺼져도 공개·RLS 우회는 남겨두지 않는다.
6. **제한 개방:** 준비된 성인 파일럿 계정만 허용하고 감사를 남긴다. 문제 발생 시 신규 시작/공개 제출을 중지하고 실행 원본과 미동기화 outbox를 보존한다.
7. **복구:** 코드를 되돌려도 새 데이터를 담은 테이블은 먼저 삭제하지 않는다. 구버전 쓰기 재개로 새 실행이 유실되지 않도록 읽기 전용/호환 복구를 우선한다. 데이터 롤백은 P00에서 검증한 백업과 이후 명령 보존 절차로만 진행한다.

## 8. 착수할 때 사용할 작업 지시

첫 개발 작업은 다음처럼 범위를 제한한다.

> **P00 적용 감사와 P01/P02 계약 준비를 진행한다.** 현재 저장 경로와 실제 DB 적용 상태를 대조하고, 기존 데이터의 소유·동의·버전 매핑 및 스테이징 백업 복원을 검증한다. 확보되지 않은 계정/환경과 D01–D09 미정값을 표시한다. 정책 초안·상태 전환표·테스트 입력표를 작성한다. 상위 시작 조건이 충족되면 P03부터 순서대로 구현한다.

이후 지시는 `Pxx 구현 + 해당 완료 기준/테스트 + 다음 티켓의 시작 가능 여부 보고`로 발행한다. 외부 조건으로 특정 티켓이 막히면 그 조건과 증거를 기록하고, 독립적인 감사/계약 자료 작업만 계속한다.

진척 보고는 아래 항목으로 통일한다.

| 구분 | 기록 내용 |
|---|---|
| 구현 | 끝난 티켓 / 진행 티켓 / 미착수 티켓 |
| DB 적용 | 로컬 파일 작성 / 스테이징 적용 / 운영 적용을 각각 기록 |
| 검증 | 정적 검사 / DB·권한 검사 / 실제 브라우저 E2E 결과를 각각 기록 |
| 제품·운영 결정 | 미확정 D항목, 담당 역할, 그 결정으로 차단된 티켓 |
| 개방 판정 | 기술·운영 게이트 통과 여부. 파일럿 실사용 수치와 혼동하지 않음 |

완료 일정은 P00/P01 이후 실제 데이터 이관 규모와 오프라인 기기 테스트 결과로 산정한다. 현재 단계에서 정해진 주차를 근거로 게이트를 생략하지 않는다. 저장 폴더·게시판·사진·BGM·구매·결제·실시간 협업·일반 공개 가입은 이 백로그에 포함하지 않는다.
